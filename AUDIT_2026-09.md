# LocalTube — Persistence, Library & Hardening Audit (September 2026)

Scope: everything between "a video is queued" and "a video plays from disk a
month later" — download persistence, rescanning, library management, library
relocation, and general hardening of the Swift ↔ WebKit app. Baseline was
`master` at 1.0.33 (build 34, commit `4a1edd7`).

Rollback point: **1.0.33 (build 34)**. The database schema (`user_version 9`)
is unchanged by this work, and the settings blob only gains optional keys, so
installing the 1.0.33 zip from GitHub Releases over this build is safe. See
*Rolling back* at the end.

---

## Findings and fixes

### Persisting videos / downloads

| # | Finding | Fix |
|---|---------|-----|
| P1 | Videos left in `queued` when the app quit were never enqueued again on relaunch. Interrupted (`downloading`) videos were flipped to `error` and needed a manual Retry each. A synced channel of 300 videos only ever downloaded the first few per session. | `DownloadService.resumePendingDownloads()` runs after the library loads and re-enqueues everything still queued/downloading (yt-dlp resumes the `.part`). `LibraryStore.healInterruptedDownloads` now re-queues instead of erroring. |
| P2 | The Retry button did nothing after a failure in the same session: `handleRetryDownload` called `enqueue`, whose de-duplication check matched the dead "failed" queue entry and returned. | Bridge now calls `retryDownload`, and `enqueue` only de-duplicates against live (waiting/active) entries. |
| P3 | State transitions were only partially persisted; `LibraryStore.updateVideo` is memory-only and callers forgot the DB write. | New `updateVideoAndPersist(_:context:)` used for every transition (queued → downloading → ready/error, cancel, retry, title fetch). |
| P4 | Channel sync computed `sortOrder` as `count + i`, so new videos got gapped, non-sequential orders. | Running counter from the current max. Same for `addVideoURLs`. |
| P5 | Sync never re-downloaded videos whose file had vanished or whose last download failed (TODO P0). | `AppState.requeueMissingAndFailed(in:)` runs after every sync (manual and daily auto-sync). |
| P6 | Playing a "ready" video whose file was gone opened a black player. | `playVideo` checks the file, re-queues it, and shows a toast. |
| P7 | `resolveToolPaths()` was never called; `yt-dlp` from pipx/MacPorts was never found, and a failed launch left the download stuck in `downloading` forever because `ShellRunner.stream` never reported launch failures. | Resolved at launch and after every dependency check; `stream` reports `launchFailedExitCode`. |
| P8 | Download failures always read "yt-dlp download failed". | The last `ERROR:` lines from yt-dlp are captured and shown ("Video unavailable", "Sign in to confirm your age", …). |
| P9 | Downloads that stopped producing output (stuck connection, hung ffmpeg) hung forever. | 10-minute inactivity watchdog terminates the process; the video goes to `error` with a clear message and the next retry resumes the `.part`. |
| P10 | Settings → Download Quality did nothing (not modelled in Swift). | `DownloadQuality` enum with yt-dlp format strings; persisted and applied. |
| P11 | The in-session download queue grew without bound. | Finished entries are trimmed to the most recent 100. |
| P12 | A yt-dlp child could outlive the app and race the resumed download on the next launch. | `applicationWillTerminate` cancels all downloads (SIGTERM, then SIGKILL). |

### Rescanning ("Verify Library")

New `LibraryMaintenanceService.verify()` — runs on launch, from Settings → Library → *Verify Now*, and from the new *Library* menu:

- confirms every ready video's file exists; heals stale absolute paths when the file is found under the current root (or by its `-<id prefix>` suffix if the title slug changed);
- puts missing videos back in the download queue;
- regenerates missing thumbnails with ffmpeg in the background;
- heals channel banner paths;
- reports leftover `.part`/`.ytdl` files and unreferenced files per channel folder (counts + bytes shown in Settings — nothing is deleted automatically).

### Library management

| # | Finding | Fix |
|---|---------|-----|
| L1 | Deleting a video or channel removed the DB row only. The confirm dialogs already claimed files would be deleted; they were not. Disk usage grew silently. | `AppState.removeVideo` deletes the video file, thumbnail and yt-dlp leftovers; `removeChannel` moves the channel folder to the Trash (permanent delete on volumes without one). Live downloads for the affected videos are cancelled first. |
| L2 | Two channels with the same display name shared one folder — deleting one would have destroyed the other's files. A name made only of emoji produced an empty folder name, dumping files into the library root. | Folder names are made unique at creation (`-2`, `-3`, …); empty names fall back to `channel-<id>`; folder deletion refuses when another channel shares the name. |
| L3 | In-memory playlists / favorites / profile assignments kept ids of deleted videos, channels and profiles (the DB cascades, memory didn't). | Pruned on every delete; React store mirrors this. |
| L4 | A brand-new install stayed on the onboarding screen forever: the bridge never set `isOnboarding = false` after the folder was chosen. | Fixed in `handleOpenFolderPicker`. |
| L5 | Profile creation seeded an "Up Next" playlist in Swift but never told React about it. | Emitted with the profile. |

### Library relocation

| # | Finding | Fix |
|---|---------|-----|
| R1 | Changing the download folder just re-pointed *new* downloads. Every existing video kept its absolute path in the old folder — the library was silently split, and if the old folder was later deleted every video broke. | Settings → Library → *Change…* now goes through a relocation flow: **Move** (physically move channel folders, rewrite paths in one transaction per channel, DB snapshot first), **Adopt** (files already moved in Finder — re-point), or **Switch** (new downloads only; old root stays a known root so its thumbnails keep serving). |
| R2 | If the library folder was unreachable at launch (external drive unplugged), settings dropped the path and the app showed onboarding; picking a folder there orphaned the whole library. | The path is kept. The app shows a "Library folder not found" screen with *Try Again* and *Locate Library…*, polls the folder every 5 s and resumes automatically. Downloads pause while it's unavailable. |
| R3 | Any new field on `AppSettings` broke JSON decoding of older saved settings, which reset everything (including the folder) and caused the same onboarding reset. | Tolerant decoding with per-key defaults. |
| R4 | Thumbnail URLs broke for any library path containing `#`, `?` or `%`. | Paths are percent-encoded on the way out; the scheme handler no longer double-decodes. |

### Hardening

| # | Finding | Fix |
|---|---------|-----|
| H1 | `ShellRunner.run` read the pipes only after the child exited. A child writing more than the pipe buffer (~64 KB) blocked forever — a `--flat-playlist` listing of a channel with a few hundred videos crosses that line, so large channel syncs "timed out". | Pipes are drained while the process runs; completion waits for exit + EOF on both pipes with a safety net for lingering grandchildren. |
| H2 | On timeout, `run` abandoned the process but never killed it. | SIGTERM, then SIGKILL after 3 s. |
| H3 | `stream` shared one unguarded buffer between the stdout and stderr readability handlers (data race). | Lock-protected line buffer. |
| H4 | No database backup before migrations. | SQLite online-backup snapshot to `Application Support/LocalTube/backups/` before any migration and before every relocation; newest 10 kept. |
| H5 | The `localtube-thumb://` handler served any image file on disk. | Restricted to files under the library root(s). |
| H6 | PIN lockout state was in memory only (relaunch reset it) and the UI showed "Incorrect PIN" while locked. | Lockout persisted; the bridge reports remaining seconds and the UI shows a countdown. Auto-submit no longer lives in an effect (StrictMode double-fire would have burned two attempts per entry). |
| H7 | `saveSettings` accepted an arbitrary `downloadFolderPath` from the WebView. | Ignored; the folder only changes through the relocation flow. |
| H8 | `AppDelegate` used force-unwrapped implicitly-unwrapped optionals (H3 from the original review). | True optionals with guards. |
| H9 | Database open failure was logged and otherwise ignored — the app looked healthy while saving nothing. | Surfaced as a blocking error screen with recovery instructions. |
| H10 | Settings "About" showed a hardcoded `v1.0.0`. | Real bundle version. |
| H11 | `.DS_Store` was tracked despite `.gitignore`. | Untracked. |

Other: window frame is remembered between launches; `sqlite3_busy_timeout` set so a previous instance still shutting down doesn't fail the open; the maximum number of parallel downloads was lowered from 6 to 4 (each yt-dlp spawns an ffmpeg for the final mux).

## Rolling back

1. Quit LocalTube.
2. Install the previous build (`LocalTube-1.0.33.zip` from GitHub Releases, or any earlier release).
3. The database is compatible as-is. If you also want to undo *data* changes made by this build (paths rewritten by a move, videos re-queued), copy the newest matching snapshot over the live database:
   ```
   cd ~/Library/Application\ Support/LocalTube
   ls backups/                       # library-pre-migration-v9-…, library-pre-relocate-move-…
   rm -f library.sqlite-wal library.sqlite-shm
   cp backups/library-pre-relocate-move-<timestamp>.sqlite library.sqlite
   ```
4. Relaunch. Settings live in `~/Library/Preferences/com.local.localtube.plist`; the keys added by this build are ignored by older builds.

Sparkle's appcast keeps every previous `<item>`, so "Check for Updates…" will not re-offer a version you rolled back from until a newer one ships.

## Verification status

- WebUI: `tsc -b`, `vite build` and ESLint on every touched file pass. (`npm run lint` on the whole tree reports 26 pre-existing errors in files this work didn't touch — mostly `react-hooks/set-state-in-effect`.)
- Swift: **not compiled in the environment this audit was produced in** (Linux, no Swift toolchain). Build with `Scripts/compile_and_run.sh` on macOS before releasing and treat compiler diagnostics as the first review pass.

## Manual test checklist

- Quit mid-download → relaunch: the video resumes without touching Retry.
- Fail a download (unplug network) → Retry works the first time.
- Delete a video, then a channel → the files are gone / the folder is in the Trash.
- Settings → Library → Change… → Move to a second folder → everything still plays; old folder empty.
- Eject the drive that holds the library → "Library folder not found"; plug it back in → app resumes by itself.
- Rename a channel folder in Finder → Verify Now re-queues its videos (paths could not be healed) — or move the whole library and use Locate/Adopt to re-point it.
- Settings → Download Quality → 480p → new downloads are 480p.
