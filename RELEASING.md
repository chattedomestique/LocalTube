# Releasing LocalTube

Releases are automatic. Merging a pull request into `master` runs
`.github/workflows/release.yml`, which on a macOS runner:

1. bumps `version.env` (patch by default),
2. builds the WebUI and the app, packages `LocalTube.app` with `Scripts/package_app.sh`,
3. signs the zip for Sparkle with the `SPARKLE_PRIVATE_KEY` secret,
4. prepends the new version to `appcast.xml`,
5. commits `Release x.y.z (build n)` + tag `vx.y.z` to `master`,
6. publishes a GitHub Release with the zip attached,
7. mirrors the appcast to the legacy Gist feed if `GIST_TOKEN` is set.

Installed copies pick the release up through **Check for Updates…**
(Sparkle) within a day, or immediately from the menu.

To cut a minor/major release, or to write release notes, run the workflow
by hand: *Actions → Release → Run workflow*.

## One-time setup: enabling auto-updates (one command)

Sparkle refuses updates that are not signed, so until the signing key is
available to CI the workflow still publishes a downloadable GitHub Release
but writes **no appcast entry**, and installs are not offered the update.

The private key was generated by `Scripts/setup-sparkle.sh` and lives in the
Keychain of the Mac that ran it. On that Mac, with `gh` logged in, run:

```bash
./Scripts/enable-auto-updates.sh
```

It exports the key from the Keychain, checks it matches the
`SPARKLE_PUBLIC_KEY` in `version.env` (a different key would break every
existing install), stores it as the `SPARKLE_PRIVATE_KEY` repository secret,
starts a Release run, waits for it, and refreshes the legacy Gist feed so
installs older than 1.0.34 see the new version too. After that every merge
to `master` ships a signed update on its own.

Manual equivalent, if you prefer:

```bash
.build/sparkle-tools/bin/generate_keys -x sparkle_private_key   # exports from Keychain
gh secret set SPARKLE_PRIVATE_KEY < sparkle_private_key
rm sparkle_private_key
```

### `SPARKLE_PRIVATE_KEY` (required for auto-update)

Stored by the script above. The public half is already in `version.env` as
`SPARKLE_PUBLIC_KEY` and must stay the same.

### `GIST_TOKEN` (optional — migrates installs ≤ 1.0.33)

Builds up to 1.0.33 read their update feed from a GitHub Gist. Builds from
1.0.34 read `appcast.xml` straight from this repository
(`APPCAST_URL` in `version.env`), which needs no token. To move the older
installs over, the Gist has to be refreshed **once more** after the first
signed release. Either:

- add a fine-grained personal access token with the *Gists: read and write*
  permission as the `GIST_TOKEN` secret (`gh secret set GIST_TOKEN`), and the
  workflow does it on every release, or
- run it once by hand after a signed release:
  `gh gist edit 7da829e5fec784a35858dbf7e44545c3 appcast.xml`.

## Manual release from a Mac

`Scripts/release.sh [patch|minor|major]` does the same steps locally, reading
the Sparkle key from the Keychain and pushing with your `gh` login.

## Rolling back

Every release is a tag + GitHub Release; install any older zip from the
Releases page. Database compatibility notes and the backup snapshots the app
takes before migrations are described in `AUDIT_2026-09.md`.
