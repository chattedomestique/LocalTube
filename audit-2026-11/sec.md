# SEC — Security & Concurrency Hardening audit (LocalTube v1.0.37)

Static review only. No Swift toolchain, no macOS. Everything about runtime WebKit/AppKit/AVFoundation behaviour is marked `suspected`. Repo untouched (git status clean at end).

Threat actors used for ranking: (1) curious child with keyboard+mouse, (2) odd/malicious YouTube title or URL, (3) local malware as same user, (4) network attacker on update/install paths.

> **Revision note (PM correction folded in):** `Player/**` is live and the player controls are native SwiftUI (`PlayerOverlayController.swift:144` hosts `PlayerControlsOverlay` from `Player/VideoPlayerView.swift:354`). Added section 9 (player panel kid-safety + concurrency), SEC-18/SEC-19 in the register, extra `Player/**` rows in the Swift 6 table, and corrected the "delete dead `Views/**`" step: `Views/Shared/TenFootStyles.swift` is still needed by live code (`Color.ltAccent`). `VideoPlayerView`, `NativePlayerView`, `ResumePromptOverlay` inside the live file are dead (only `Views/Viewer/ViewerRootView.swift:19` references them).

## 0. Verdict

The code-injection class of bugs from the March review is genuinely fixed (JS interpolation, `curl|bash`, SQL, path traversal, handler leak). Subprocess handling is clean: argv only, no shell anywhere, titles slugged to `[a-z0-9-]`. The weak spot has moved from *injection* to *authorization and kid-safety integrity*: the Swift bridge has **no authorization at all** (React hides buttons; Swift trusts every message), a PIN-free "Locate Library…" path exists on the drive-unplugged screen, native menu items bypass the PIN, the web view has no navigation policy, the edit/admin session never expires, and PIN recovery is a dead feature that leaves a plaintext secret in UserDefaults. The release pipeline auto-signs and ships every master merge to every family's Mac behind a single repo secret. Concurrency: real runtime data-race risk is low (nearly everything is `@MainActor`/actor/lock-boxed); Swift 6 is a compile-time hygiene task of roughly 25-45 diagnostics in live code, not a safety emergency.

## 3. Kid-safety checklist (every way out of Viewer mode)

- Menu: `⌘E` Enter Editor Mode = PIN gated (good). `⌘,` Settings = ungated at menu level (SEC-3). Library > Reveal Library Folder / Reveal Logs / Verify = ungated (SEC-3). App > Check for Updates = ungated (harmless: EdDSA verified). `⌘Q`, `⌘H`, `⌘M`, `⌃⌘F` exist; the app is not a kiosk, so a child can always quit/leave; Dock menu: none.
- Window red button quits the app (`WebWindowController.swift:288`); relaunch always starts in Viewer (mode is not persisted) - good.
- Web UI keyboard: only two global key handlers exist (`LtSelect.tsx:47`, `PlayerScreen.tsx:364`, the latter legacy); no hidden shortcut reaches admin.
- Native player panel: Esc closes player only (`PlayerOverlayController.swift:303`); no destructive controls.
- PIN: 4-digit only in UI, escalating persisted lockout (SEC-8), no per-profile lock (SEC-7), recovery gap (SEC-6), session never expires (SEC-5), drive-unplugged hole (SEC-2), drag/drop navigation (SEC-4).
- Content: downloads are always `https://www.youtube.com/watch?v=<id>`; UI substring check `includes('youtube.com/watch')` (`AddVideosModal.tsx:16-26`) is spoofable but Swift coerces the host anyway. No age-limit, no review queue (SEC-7).

## 6. Concurrency / Swift 6 readiness

### 6.1 Actual risk picture (static)
Already safe: `DatabaseService` is an `actor` (all SQLite pointers actor-isolated); `AppState`, `LibraryStore`, `DownloadService`, `DependencyService`, `LibraryMaintenanceService`, `LocalTubeBridge`, `BridgeEventEmitter`, `WebWindowController`, `PlayerOverlayController`, `PlayerState`, `DownloadQueueItem`, `AppDelegate` are `@MainActor`; `ShellRunner` shares state only through lock-boxes (`AtomicFlag`, `AtomicValue`, `CompletionGate`, `OutputCollector`, `LineBuffer`, `ErrorLineCollector`, `URLCollector` - `ShellRunner.swift:318-422`, `DownloadService.swift:546`, `ChannelResolverService.swift:108`); models are `Sendable` structs; the slow filesystem passes use `Task.detached` with Sendable captures (`LibraryMaintenanceService.swift:211,525,630,773,804`; `AppState.swift:532`). `AppLogger` mutable statics are only touched on its private serial queue (`AppLogger.swift:10-11,21,52-56`).

Remaining real (runtime) hazards, all low:
- Fire-and-forget `Task { await persist(...) }` per write (`LibraryStore.swift:449,474,481,506,542,559`) gives no ordering guarantee between e.g. `insertChannel` and a following `insertVideo` (FK `ON`), so a fast add-channel-then-add-video can lose a row (logged only). Route writes through one serial queue (an `AsyncStream` consumer inside `LibraryStore`).
- `PINService.verify` read-modify-write on UserDefaults (`:91-101`) is only safe because all callers are on the main actor; mark it `@MainActor` to make that a compile-time fact.
- `PlayerPanel.keyDown` hops through `Task { @MainActor ...}` (`PlayerOverlayController.swift:299-315`), delaying key handling by a runloop turn and capturing a non-Sendable `NSEvent`.
- `ShellRunner` grandchild safety nets use `DispatchQueue.global().asyncAfter` and read `process.isRunning` off-main (`:102,201,253`); fine on Foundation's thread-safe `Process`, but not provably Sendable.

### 9.2 Concurrency review of the player path
Good: `PlayerState` is `@Observable @MainActor`; observer closures hop with `Task { @MainActor }`; both `AVPlayerItemDidPlayToEndTime` registrations use `queue: .main`; tokens are removed on dismiss (`PlayerOverlayController.swift:180-183,254-257`).
Hazards (all `confirmed` as code patterns, runtime effect `suspected`):
1. **Stale readiness task.** `PlayerState.play` (`:49-72`) spawns an un-cancelled `Task` that polls `item.status` for up to 10 s, then `seek`s and `play()`s the *player* (not that item) and assigns `self.duration`. If `play` is called again quickly (queue advance, tapping another video, stop then show) the old task can seek/play the new item and overwrite its duration. Fix: keep `playTask`, cancel in `play`/`stop`, and guard `player.currentItem === item` and `!Task.isCancelled` before each mutation. Effort S.
2. **Two end-of-item observers mutating shared state.** `PlayerState.itemEndObserver` (`:171-189`, sets `isPlaying = false`, resets the ended video's resume position) and `PlayerOverlayController.observePlayerStop` (`:184-193`, advances or dismisses) both fire on every item end with `object: nil`. It works only because registration order is deterministic and Tasks run FIFO on the main actor; if either is reordered, `playNext` can be followed by `isPlaying = false` and a reset of the *next* video's resume position. Fix: one observer owned by `PlayerState` that calls an `onItemEnded` closure (the controller's advance logic). Effort S.
3. **Trap-prone teardown.** `PlayerState.cleanup()` is `nonisolated` and uses `MainActor.assumeIsolated` (`:192-202`); it is called from `PlayerOverlayController.deinit` (`:268-275`, nonisolated). If the last release ever happens off the main thread this traps; it also does not nil the tokens (double removal if called twice). Fix: `@MainActor func cleanup()` called from `dismiss`/an explicit `teardown()`, tokens set to nil.
4. **`keyDown` async hop.** `PlayerPanel.keyDown` wraps handling in `Task { @MainActor }` capturing `NSEvent` (`:299-315`): delays handling by a runloop turn, ignores `isARepeat`/modifiers, and is a Swift 6 Sendable diagnostic. Fix: handle synchronously (the method is already main-actor).
5. Periodic observer saves resume position on every 0.5 s tick inside `< 0.55 s` of a 5 s boundary, so usually twice per boundary (`:164`); harmless but doubles DB writes. Fix: track `lastSavedBucket`.
6. `scheduleControlsHide` (`:119-132`) uses `Task` + redundant `MainActor.run`; fine.
